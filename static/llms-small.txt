# BurgerAPI - Essential Reference

BurgerAPI is a Bun-first, WinterCG-compatible API framework with file-based routing, six lifecycle hooks, plugins, providers, Standard Schema (Zod) validation, automatic OpenAPI generation, and WebSocket support.

**Current release:** `burger-api` and `@burger-api/cli` are at `1.0.0-beta` (public beta, not yet recommended for production). The previous stable line is `0.9.x`: `burger-api@0.9.7` / `@burger-api/cli@0.9.9`. Beta notes: https://burger-api.com/blog/burger-api-v1.0.0-beta-release

Full documentation: https://burger-api.com/llms-full.txt

## Install and Run

```bash
bun add burger-api
bun add -g @burger-api/cli

# scaffold and run (works without a global install)
bunx @burger-api/cli create my-app
cd my-app
bun run dev
```

## Project Layout

```
src/
├── index.ts            # new Burger(...) + serve()
├── hooks.ts            # global lifecycle hooks
├── plugins.ts          # burger.usePlugin(...)
├── providers.ts        # burger.provide(name, service) -> ctx.services
├── openapi.config.ts   # OpenAPI metadata and docs UI (dev auto-discovery)
├── api/                # API routes (apiDir)
├── pages/              # page routes (Bun-only)
└── websocket/          # WebSocket routes (wsDir, default src/websocket/)
burger.build.ts          # build-time config for the CLI (never shipped at runtime)
```

## Burger Class

```typescript
import { Burger } from 'burger-api';

const app = new Burger({
    apiDir: './src/api',
    apiPrefix: 'api',        // default 'api'
    pageDir: './src/pages',
    wsDir: './src/websocket',
    title: 'My API',         // OpenAPI document metadata
    version: '1.0.0',
    description: 'API description',
    debug: false,
    validation: { status: 422 }, // ValidatorConfig; default status is 422
});

await app.serve(4000);
```

Other options include `apiRoutes`, `pageRoutes`, `wsRoutes`, `assetRoutes`, `globalHooks`, `providersModule`, `openapi`, and `runtimeTarget`. In production builds the CLI passes pre-resolved modules and route lists so no filesystem scanning happens at runtime.

## BurgerContext

Every handler and hook receives one context object, `ctx`:

- `ctx.request`: the incoming standard `Request`
- `ctx.params`: dynamic route params (`/users/:id` -> `{ id }`)
- `ctx.wildcardParams`: array of wildcard segments
- `ctx.query`: lazily parsed query object
- `ctx.headers`: request headers
- `ctx.validated`: validated data from `schema.ts` (`params`, `query`, `body`, `headers`, `cookies`)
- `ctx.services`: services registered via `src/providers.ts` / `burger.provide()`
- `ctx.route`, `ctx.config`: route metadata and `config.ts` options (typed via module augmentation)
- `ctx.set`: response mutations (`status`, `headers`) applied in one step
- Request helpers: `ctx.json()`, `ctx.text()`, `ctx.formData()`

Handlers return a standard Web `Response`:

```typescript
export async function GET(ctx: BurgerContext) {
    return Response.json({ hello: 'world' });
}
```

## File-Based Routing

A route is a directory of sibling convention files:

| File         | Role                                                                 |
|--------------|----------------------------------------------------------------------|
| `route.ts`   | `export async function GET(ctx: BurgerContext)` (one export per method) |
| `schema.ts`  | Per-method validation: `export const GET = { params, query, body, headers, cookies }` |
| `hooks.ts`   | Route-scoped hooks                                                     |
| `openapi.ts` | Per-method OpenAPI metadata                                           |
| `config.ts`  | Route options (auth, cache, timeout, ...), typed via `RouteConfig` augmentation |

```typescript
// api/users/[id]/route.ts
import type { BurgerContext } from 'burger-api';

export async function GET(ctx: BurgerContext) {
    return Response.json({ id: ctx.params.id });
}
```

Routing patterns:

```
api/users/route.ts        -> /api/users
api/users/[id]/route.ts   -> /api/users/:id      (ctx.params.id)
api/files/[...]/route.ts  -> /api/files/*        (ctx.wildcardParams)
api/(admin)/users/route.ts -> /api/users         (groups are URL-only)
```

- Route directories are self-contained: no folder or group inheritance.
- Do not mix wildcard (`[...]`) and dynamic (`[id]`) folders at the same level.
- Do not add two dynamic folders (`[id]` and `[slug]`) at the same level.
- `.ts`, `.js`, and `.mjs` route files all work; JavaScript projects get full JSDoc type-checking.

## defineRoute / defineHooks

`defineRoute(schema, handler)` and `defineHooks(schema, hooks)` infer `ctx.validated` from the schema per method, so no generic has to be written by hand:

```typescript
// api/users/[id]/schema.ts
import { z } from 'zod';
export const GET = { params: z.object({ id: z.string() }) };

// api/users/[id]/route.ts
import { defineRoute } from 'burger-api';
import { GET as GETSchema } from './schema';

export const GET = defineRoute(GETSchema, async (ctx) => {
    return Response.json({ id: ctx.validated.params.id });
});
```

## Hooks

Six lifecycle stages:

| Hook | When |
|------|------|
| `onRequest` | Request enters the app (global/plugin only) |
| `transform` | After routing, before validation; context decoration factory map |
| `beforeRoute` | After validation, before the handler |
| `afterRoute` | After the handler returns |
| `mapResponse` | Before the response is sent (final headers) |
| `onError` | Any error in the lifecycle |

Pipeline: `onRequest -> Routing -> transform -> Validation -> beforeRoute -> Handler -> afterRoute -> mapResponse`. Errors jump to `onError`.

Scopes and order:

- Forward hooks (`onRequest`, `beforeRoute`): Framework -> Plugin -> Global -> Route
- Response hooks (`afterRoute`, `mapResponse`) and error hooks (`onError`): Route -> Global -> Plugin -> Framework

Route `hooks.ts` can export `transform`, `beforeRoute`, `afterRoute`, `mapResponse`, and `onError`. `onRequest` is app-level only: global `src/hooks.ts` or plugins (`RouteHooks` excludes it; `GlobalHooks` adds it).

Return values: a hook can return a `Response` to stop the chain, a function to transform the final response, or `undefined` to continue.

```typescript
// src/hooks.ts
export const onRequest = [
    async (ctx) => {
        console.log(`${ctx.request.method} ${ctx.request.url}`);
    },
];

// api/protected/hooks.ts
export const beforeRoute = [
    async (ctx) => {
        if (!ctx.headers.get('Authorization')) {
            return Response.json({ error: 'Unauthorized' }, { status: 401 });
        }
    },
];
```

## Validation

Validation runs after `transform` and before `beforeRoute`. Schemas are written in `schema.ts` with Zod (or any Standard Schema library), per method:

```typescript
// api/users/schema.ts
import { z } from 'zod';

export const GET = {
    query: z.object({ page: z.coerce.number().int().min(1).default(1) }),
};

export const POST = {
    body: z.object({ name: z.string().min(1), email: z.email() }),
};
```

Read validated data from `ctx.validated`; with `defineRoute`/`defineHooks` it is fully typed. In plain handlers it is optional and typed `unknown`.

On failure, the framework throws `ValidationError` and `onError` produces a 422 response with an RFC 9457 `application/problem+json` body by default:

```json
{
    "type": "about:blank",
    "title": "Validation Error",
    "status": 422,
    "errors": {
        "body": [{ "path": ["email"], "message": "Invalid email" }]
    }
}
```

`new Burger({ validation: { ... } })` adjusts the default error status and the error format.

## Plugins and Providers

Hooks and plugins are separate: hooks control the request lifecycle, plugins extend the application.

```typescript
// src/plugins.ts
import type { PluginRegistrar } from 'burger-api';
import { apiKey } from './ecosystem/plugins/api-key/api-key';

export default (burger: PluginRegistrar) => {
    burger.usePlugin(apiKey({ keys: ['demo-api-key-123'] }));
};
```

```typescript
// src/providers.ts
import type { ProviderRegistrar } from 'burger-api';

export default (burger: ProviderRegistrar) => {
    burger.provide('db', createDatabase());
};
// Usage: ctx.services.db
```

Official ecosystem plugins live under `ecosystem/plugins/`: `jwt-auth`, `api-key`, `basic-auth`, `session`, `oidc`, `env`. Official hooks live under `ecosystem/hooks/`: `cors`, `logger`, `rate-limiter`, `cache`, `compression`, `security-headers`, `body-size-limiter`, `timeout`.

## WebSocket

File-based routes live under `wsDir` (default `src/websocket/`); the folder name becomes the URL:

```typescript
// src/websocket/chat/ws.ts
import type { BurgerWS } from 'burger-api';

export function open(ws: BurgerWS) {
    ws.send('connected');
}

export function message(ws: BurgerWS, message: string | Buffer) {
    ws.send(message);
}

export function close(ws: BurgerWS, code: number, reason: string) {}
```

Programmatic routes work too:

```typescript
const app = new Burger({
    wsRoutes: [{ path: '/chat', handlers: { open(ws) { ws.send('hi'); } } }],
});
```

Route params are available as `ws.data.route.params`. Pub/sub is available through `ws.subscribe`/`ws.unsubscribe`/`ws.publish`. WebSocket routes work on Bun, Node (via `@burger-api/node-server` or `createNodeWsBridge()`), Cloudflare, and Deno. Vercel does not support WebSocket. Pages (`src/pages/`) are Bun-only.

## OpenAPI

The spec is generated from routes and schemas; the raw spec is served at `/openapi.json` and interactive docs at `/docs` (Swagger UI by default, with `scalarDocs()` and `redocDocs()` alternatives). Document metadata is set on `new Burger({ title, version, description })`; per-route metadata is exported per method from `openapi.ts` (`summary`, `description`, `tags`, `operationId`, `deprecated`, `responses`, `externalDocs`).

## CLI

Real commands: `create`, `add`, `list` (alias `ls`), `skills install|list|available`, `dev`, `start`, `build`, `build:exec`, `generate` (`route|hook|plugin|ws`), `inspect`, `doctor`.

```bash
burger-api create my-api --lang ts      # -y/--yes for defaults
burger-api list                         # ecosystem catalog
burger-api add cors logger rate-limiter
burger-api generate route users         # also: hook, plugin, ws
burger-api dev                          # -p/--port, -f/--file
burger-api start                        # run the built bundle
burger-api build src/index.ts --target=cloudflare
burger-api build:exec src/index.ts
burger-api inspect --json               # resolved project shape
burger-api doctor --json                # project health checks
```

`add`, `list`, and `skills` fetch their catalog from GitHub (`isfhan/burger-api`). Until the ecosystem content lands on `main`, set `BURGER_API_BRANCH=feat/burger-api-v1` for those commands.

## Deploy Targets

`burger-api build --target=bun|node|cloudflare|deno|vercel` generates the entry file and platform config for each target. API routes are portable to all five; pages are Bun-only; Vercel does not support WebSocket. For WinterCG runtimes, `toFetchHandler()` adapts the app to a `fetch` handler. `@burger-api/node-server` is the official Node adapter, and standalone executables come from `burger-api build:exec`.

## Key Features

- Bun-native performance with a hybrid router (native dispatch first, radix trie fallback)
- File-based routing with per-route convention files
- Six lifecycle hooks plus plugins and providers
- Zod / Standard Schema validation with typed `ctx.validated`
- Automatic OpenAPI 3.0 generation with Swagger, Scalar, and Redoc UIs
- WebSocket routes with pub/sub
- Full TypeScript and JavaScript support
- One-flag builds for Bun, Node, Cloudflare, Deno, and Vercel
