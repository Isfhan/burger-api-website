# Welcome to BurgerAPI

BurgerAPI is a Bun-first framework for building APIs. You create folders and files, and BurgerAPI turns them into routes. It works with TypeScript and JavaScript.

:::info A new BurgerAPI
`burger-api` and `@burger-api/cli` 1.0.0-beta are rebuilt from the ground up and install by default. Please try them and [open an issue](https://github.com/isfhan/burger-api/issues) if anything breaks or feels wrong. See the [release notes](https://burger-api.com/blog/burger-api-v1.0.0-beta-release) for what is new. Coming from `burger-api@0.9.7` or `@burger-api/cli@0.9.9`? The [migration guide](https://burger-api.com/docs/migration) covers every breaking change.
:::

### What you get

- **File-based routing:** a folder with a `route.ts` file is a route.
- **Validation:** define schemas in `schema.ts` and read typed data from `ctx.validated`.
- **Hooks:** run code at each step of a request, for example to log or check auth.
- **Plugins and providers:** add features in `src/plugins.ts` and shared services in `src/providers.ts`.
- **OpenAPI:** API docs generated from your routes, served at `/docs`.
- **WebSocket:** real-time routes under `src/websocket/`.
- **Deploy anywhere:** `burger-api build --target=bun|node|cloudflare|deno|vercel`.

# Quick Start

Get a BurgerAPI app running in under a minute.

## Prerequisites

- **[Bun](https://bun.sh/)**: the CLI and the dev server run on Bun, wherever you deploy later.

## Steps

1. **Install the CLI:**

    ```bash
    bun add -g @burger-api/cli
    ```

    You can also skip the install and run `bunx @burger-api/cli <command>`.

    If you see `burger-api: command not found`, add `~/.bun/bin` to your `PATH` (`%USERPROFILE%\.bun\bin` on Windows) and open a new terminal.

2. **Create a project and start the dev server:**

    ```bash
    burger-api create my-api
    cd my-api
    bun run dev
    ```

3. **Open** [http://localhost:4000/api](http://localhost:4000/api) for the starter route and [http://localhost:4000/docs](http://localhost:4000/docs) for the API docs.

## JavaScript

The project uses TypeScript by default. For JavaScript, pass `--lang js`:

```bash
burger-api create my-api --lang js
```

See [JavaScript](https://burger-api.com/docs/javascript).

## Deploy anywhere

When you are ready to ship, build for your platform: `bun` (default), `node`, `cloudflare`, `deno`, or `vercel`.

```bash
burger-api build src/index.ts --target=cloudflare
```

See [Deployment](https://burger-api.com/docs/deployment/bun) for each target and [Compatibility](https://burger-api.com/docs/compatibility) for what works where.

# Installation

BurgerAPI runs on [Bun](https://bun.sh/). Install Bun 1.4.4 or newer first ([guide](https://bun.sh/docs/installation)), then check it:

```bash
bun --version
```

## Install the CLI

The `burger-api` CLI creates projects and adds hooks and plugins. Pick one way to install it:

- **With Bun** (recommended):

  ```bash
  bun add -g @burger-api/cli
  ```

  If you then see `burger-api: command not found`, add `~/.bun/bin` to your `PATH` (`%USERPROFILE%\.bun\bin` on Windows) and open a new terminal.

- **With the install script**, which installs a standalone executable:

  ```bash
  # macOS, Linux, WSL
  curl -fsSL https://burger-api.com/install.sh | bash
  ```

  ```powershell
  # Windows PowerShell
  irm https://burger-api.com/install.ps1 | iex
  ```

- **From [GitHub Releases](https://github.com/isfhan/burger-api/releases/latest)**: download the executable for your system and put it on your `PATH`. On Linux and macOS, run `chmod +x burger-api`.

You can also run it once without installing: `bunx @burger-api/cli create my-api`.

## Create and run a project

```bash
burger-api create my-api
cd my-api
bun run dev
```

See the [CLI Tool](https://burger-api.com/docs/getting-started/cli) guide for every command.

## Update

:::tip Getting an error?
Update the CLI and the framework first. Most problems are already fixed there.
:::

```bash
bun add -g @burger-api/cli@latest   # the CLI (or run the install script again)
bun add burger-api@latest           # the framework, in your project
burger-api doctor                   # finds hooks and plugins to refresh
```

Hooks and plugins you added with `burger-api add` are copies in your project, so these updates do not change them. `burger-api doctor` tells you which ones are out of date and prints the command to refresh each one. See [Add Command](https://burger-api.com/docs/cli/add#updating-a-copy).

Run `burger-api --version` to see which version you have. If it still shows an old version, another `burger-api` comes first on your `PATH`: remove it, or run the install script, which tells you where it is.

## Without the CLI

You can also set up a project by hand:

1. Create a Bun project and install BurgerAPI and Zod:

   ```bash
   bun init
   bun add burger-api zod
   ```

2. Create your entry file:

   ```typescript title="src/index.ts"
   import { Burger } from "burger-api";

   const app = new Burger({
     apiDir: "./src/api",
   });

   const port = Number(process.env.PORT) || 4000;
   app.serve(port, () => {
     console.log(`Server running on http://localhost:${port}`);
   });
   ```

3. Create your first route. Validation goes in the route's `schema.ts`:

   ```typescript title="src/api/schema.ts"
   import { z } from "zod";
   import type { MethodSchema } from "burger-api";

   export const GET = {
     query: z.object({ name: z.string().default("world") }),
   } satisfies MethodSchema;
   ```

   ```typescript title="src/api/route.ts"
   import { defineRoute } from "burger-api";
   import { GET as GetSchema } from "./schema";

   export const GET = defineRoute(GetSchema, (ctx) => {
     return Response.json({ message: `Hello, ${ctx.validated.query.name}!` });
   });
   ```

4. Run it:

   ```bash
   bun run src/index.ts
   ```

   Open `http://localhost:4000/api` (try `?name=Burger`) and `http://localhost:4000/docs`.

Next, see [Configuration](https://burger-api.com/docs/core/configuration) to learn how to set up your app.

# Burger API CLI Tool

The `burger-api` CLI creates projects, adds hooks and plugins, runs your app while you develop, and builds it for production. Install it as described in [Installation](https://burger-api.com/docs/getting-started/installation).

## Quick start

```bash
burger-api create my-api
cd my-api
bun run dev
```

Open `http://localhost:4000/api` and `http://localhost:4000/docs`. See [Quick Start](https://burger-api.com/docs/quick-start) for the full walkthrough.

## Commands

| Command | What it does |
|---------|--------------|
| [`create <name>`](https://burger-api.com/docs/cli/create) | Creates a new project. |
| [`dev`](https://burger-api.com/docs/cli/dev) | Runs your app and restarts it when you save a file. |
| [`build`](https://burger-api.com/docs/cli/build) | Builds your app for Bun, Node, Cloudflare Workers, Deno or Vercel. |
| `start` | Runs the Bun build from `burger-api build`. |
| [`build:exec`](https://burger-api.com/docs/cli/build-exec) | Builds a single executable that runs without Bun installed. |
| [`list`](https://burger-api.com/docs/cli/list) | Shows the official hooks and plugins. |
| [`add <name...>`](https://burger-api.com/docs/cli/add) | Copies official hooks and plugins into your project. |
| [`generate <type> <name>`](https://burger-api.com/docs/cli/generate) | Creates a route, WebSocket route, hook or plugin from a template. |
| [`inspect`](https://burger-api.com/docs/cli/inspect) | Shows the routes, hooks and plugins the CLI finds in your project. |
| [`doctor`](https://burger-api.com/docs/cli/doctor) | Checks your project for problems. |
| [`skills`](https://burger-api.com/docs/cli/skills) | Installs AI agent skills into your project. |

Run `burger-api <command> --help` to see every option.

### `start`

`burger-api start` runs `.build/bundle/app.js`, the output of `burger-api build` for Bun. If you change your code after building, `start` warns that the build is out of date: run `burger-api build` again. For other targets, run the build with the platform's own tool. See [Deployment](https://burger-api.com/docs/deployment/bun).

```bash
burger-api build
burger-api start
```

## Project structure

`burger-api create` generates:

```text
my-api/
├── src/
│   ├── index.ts           # App entry
│   ├── hooks.ts           # Global hooks
│   ├── plugins.ts         # Plugins
│   ├── providers.ts       # Shared services
│   ├── openapi.config.ts  # OpenAPI and docs page settings
│   ├── types.ts           # App-wide types (TypeScript projects)
│   └── api/               # API routes
├── AGENTS.md              # Project rules for AI agents
├── burger.build.ts        # Build settings
├── package.json
└── tsconfig.json          # jsconfig.json in a JavaScript project
```

`burger-api add` creates `ecosystem/` for the hooks and plugins it copies.

## Environment variables

- `GITHUB_TOKEN`: used when the CLI downloads hooks, plugins and skills from GitHub. Set it if you hit GitHub's rate limit.
- `BURGER_API_LOCAL`: set to `1` to turn on [local mode](#local-mode).

## Troubleshooting

- **`burger-api: command not found`**: the folder with the `burger-api` executable is not on your `PATH`. Restart your terminal after installing. See [Installation](https://burger-api.com/docs/getting-started/installation).
- **`Directory already exists`**: `create` needs a folder name that does not exist yet.
- **Could not fetch the hooks and plugins list**: the CLI could not reach GitHub. Check your connection.
- **Entry file not found**: run the command from your project root, or pass the entry with `-f`.

## Local mode

For working on BurgerAPI itself: `--local` (or `BURGER_API_LOCAL=1`) makes the CLI use your local checkout instead of npm and GitHub. See `LOCAL_TESTING.md` in the [burger-api repository](https://github.com/isfhan/burger-api).

# Key Concepts

These are the main ideas in BurgerAPI. Each section links to a page with more detail.

## File-based routing

Your folders are your URLs. A folder under `src/api/` with a `route.ts` file is a route. Next to it you can add `schema.ts`, `hooks.ts`, `openapi.ts`, and `config.ts`. Each route folder stands on its own: child folders do not inherit these files.

See [File-Based Routing](https://burger-api.com/docs/routing/file-based-routing).

## Burger instance

`src/index.ts` creates one `Burger` instance and starts the server. Build settings live in `burger.build.ts` and are read by the CLI.

See [Burger Class](https://burger-api.com/docs/core/burger-class) and [Configuration](https://burger-api.com/docs/core/configuration).

## Context

Every handler gets one object, `ctx` (type `BurgerContext`). It holds the request, `ctx.params`, `ctx.query`, validated data in `ctx.validated`, and your services in `ctx.services`. Handlers return a standard `Response`.

```ts
import type { BurgerContext } from "burger-api";

export async function GET(ctx: BurgerContext) {
    return Response.json({ id: ctx.params.id });
}
```

See [Request Context](https://burger-api.com/docs/core/request-handling).

## Validation

Define a schema per method in `schema.ts`. BurgerAPI checks the request before your handler runs. Bad input gets a `422` error. Wrap the handler in `defineRoute(schema, handler)` to get `ctx.validated` typed for you.

See [Zod Validation](https://burger-api.com/docs/validation/zod) and [Type Safety](https://burger-api.com/docs/advanced/type-safety).

## Hooks and plugins

- **Hooks** run at steps of a request: `onRequest`, `transform`, `beforeRoute`, `afterRoute`, `mapResponse`, `onError`. Put global hooks in `src/hooks.ts` and route hooks in the route's `hooks.ts`.
- **Plugins** add features to your app. Register them in `src/plugins.ts`.
- **Providers** register shared services in `src/providers.ts`. You read them from `ctx.services`.

See [Hooks](https://burger-api.com/docs/hooks/system) and [Ecosystem](https://burger-api.com/docs/ecosystem/introduction).

## OpenAPI

BurgerAPI builds an OpenAPI document from your routes and schemas. It serves the docs UI at `/docs`.

See [OpenAPI & Swagger](https://burger-api.com/docs/api/openapi).

## CLI and deployment

The CLI creates projects (`create`), adds hooks and plugins (`add`), runs the dev server (`dev`), and builds for production (`build`). Pick a platform with `--target`: `bun` (default), `node`, `cloudflare`, `deno`, or `vercel`.

WebSocket routes work on every target except Vercel.

See [CLI Tool](https://burger-api.com/docs/getting-started/cli), [Deployment](https://burger-api.com/docs/deployment/bun), and [Compatibility](https://burger-api.com/docs/compatibility).

# Routing

BurgerAPI uses file-based routing. The folders and files under your API directory become HTTP routes. You do not register routes by hand.

- `products/route.ts` becomes `/api/products`.
- A folder named `[id]` captures one segment into `ctx.params.id`.
- A folder named `[...]` captures the rest of the path into `ctx.wildcardParams`.
- A folder named `(group)` organizes files and does not appear in the URL.

When several routes match, the most specific wins: static, then `[param]`, then `[...]`.

See [File-Based Routing](https://burger-api.com/docs/routing/file-based-routing) for the full guide.

# Hook System

Hooks let you run code at fixed points of a request. Use them for auth, logging, headers and error handling.

Hooks and plugins are separate things. A hook runs at one point of a request. A plugin is a package of hooks that you register in `src/plugins.ts`.

## The six hooks

| Hook | When it runs |
|------|------|
| `onRequest` | The request enters the app, before routing |
| `transform` | After routing, before validation. Adds fields to `ctx` |
| `beforeRoute` | After validation, before the handler |
| `afterRoute` | After the handler returns |
| `mapResponse` | Right before the response is sent |
| `onError` | When an error is thrown |

```
onRequest -> Routing -> transform -> Validation -> beforeRoute
  -> Handler -> afterRoute -> mapResponse
```

An error thrown in any step goes to `onError`. A request that matches no route gets a 404.

## What a hook returns

- `undefined`: continue.
- A `Response` from `onRequest` or `beforeRoute`: stop here and send this response. The handler does not run. `afterRoute` and `mapResponse` still run on it.
- A `Response` from `afterRoute` or `mapResponse`: replace the current response.
- A function `(response) => Response`: change the response.

See [Hook Return Types](https://burger-api.com/docs/hooks/return-types) for details and examples.

```ts title="src/api/users/hooks.ts"
import type { RouteHooks } from "burger-api";

export const beforeRoute: RouteHooks["beforeRoute"] = [
  (ctx) => {
    if (!ctx.headers.get("x-api-key")) {
      return new Response("Unauthorized", { status: 401 });
    }
  },
];
```

## Where hooks live

- **Global**: `src/hooks.ts`. See [Global Hooks](https://burger-api.com/docs/hooks/global).
- **Route**: `hooks.ts` next to a `route.ts`. See [Route Hooks](https://burger-api.com/docs/hooks/route-specific).
- **Plugin**: the `hooks` of a plugin registered in `src/plugins.ts`. See [Hooks and Plugins](https://burger-api.com/docs/ecosystem/hooks-plugins).

Global and plugin `afterRoute` and `mapResponse` run for every response: 404s, errors, pages, assets and `/docs` too. Route hooks run only when their route matches.

`onRequest` is not allowed in a route `hooks.ts`. It runs before routing, so put it in `src/hooks.ts` or a plugin.

Hooks are not inherited. A route's `hooks.ts` applies to that route only, not to sub-folders.

## Order

- `onRequest`, `transform`, `beforeRoute`: plugin hooks first, then global, then route.
- `afterRoute`, `mapResponse`, `onError`: route hooks first, then global, then plugin.

## Auth goes in transform

`transform` runs before validation. If you check auth there, a caller without a token gets a 401, not a 422 that lists your schema fields. Throw `UnauthorizedError` to reject. Use `beforeRoute` for checks that need `ctx.validated`.

## Changing status and headers

Set `ctx.set.status` and `ctx.set.headers` from any hook or handler. See [Response Mutation](https://burger-api.com/docs/api/response-mutation).

# Zod Validation

BurgerAPI uses [Zod](https://zod.dev/) 4 to check requests. You write a schema in `schema.ts`. BurgerAPI checks the request before your handler runs and puts the typed result on `ctx.validated`.

You can validate `query`, `params`, `headers`, `cookies` and `body`.

```ts title="api/products/schema.ts"
import { z } from "zod";

export const GET = {
  query: z.object({
    limit: z.coerce.number().int().min(1).max(100).optional(),
  }),
};
```

```ts title="api/products/route.ts"
import { defineRoute } from "burger-api";
import { GET as GetSchema } from "./schema";

export const GET = defineRoute(GetSchema, (ctx) => {
  const { limit } = ctx.validated.query; // number | undefined
  return Response.json({ limit });
});
```

`defineRoute` gives `ctx.validated` the types from your schema. To reuse a slot type elsewhere, use `z.infer<typeof GET.query>`.

`z.coerce.number()` turns the text `"50"` into the number `50`. To convert text for the whole app, see [Coercion](https://burger-api.com/docs/validation/coercion).

Other schema libraries work too. See [Standard Schema Support](https://burger-api.com/docs/validation/standard-schema).

# Request API

Every handler and hook gets `ctx`, a `BurgerContext`. This page lists what you can read from it.

Examples assume `import type { BurgerContext } from "burger-api";`.

## Quick reference

| Property | What it is |
|----------|------------|
| `ctx.params` | Path parameters from `[param]` folders |
| `ctx.wildcardParams` | Segments matched by a `[...]` folder |
| `ctx.query` | Query string values. See [Query Parsing](https://burger-api.com/docs/api/query-parsing) |
| `ctx.cookies` | Cookies, by name |
| `ctx.headers`, `ctx.method`, `ctx.url` | The usual request fields |
| `ctx.json()`, `ctx.text()`, `ctx.arrayBuffer()` | Read the body |
| `ctx.body` | The raw body stream |
| `ctx.request` | The original `Request` |
| `ctx.validated` | Data that passed your schemas |
| `ctx.route` | The matched route. See [Route Metadata](https://burger-api.com/docs/api/route-metadata) |
| `ctx.config` | The route's `config.ts` values, read-only |
| `ctx.services` | Services from `src/providers.ts` |
| `ctx.ip` | The client address |
| `ctx.set` | Status, headers and cookies for the response. See [Response Mutation](https://burger-api.com/docs/api/response-mutation) |

## Params and query

```ts title="src/api/users/[id]/route.ts"
export async function GET(ctx: BurgerContext) {
  const { id } = ctx.params;
  const { limit = "10" } = ctx.query;
  return Response.json({ id, limit });
}
```

## Body

```ts
export async function POST(ctx: BurgerContext) {
  const body = await ctx.json<{ name: string }>();
  return Response.json({ name: body.name });
}
```

You can call `ctx.json()` more than once. If the route has a `body` schema, read `ctx.validated.body` instead. It is typed and already checked.

## ctx.validated

Add a `schema.ts` and wrap the handler with `defineRoute`. `ctx.validated` is then typed from the schema.

```ts title="src/api/products/schema.ts"
import { z } from "zod";

export const GET = { query: z.object({ limit: z.coerce.number().optional() }) };
```

```ts title="src/api/products/route.ts"
import { defineRoute } from "burger-api";
import { GET as GetSchema } from "./schema";

export const GET = defineRoute(GetSchema, (ctx) => {
  const { limit } = ctx.validated.query; // number | undefined
  return Response.json({ limit });
});
```

See [Validation](https://burger-api.com/docs/core-concepts/validation).

## ctx.services

Shared services such as a database client. They are the same for every request and read-only. For per-request values, use a [transform](https://burger-api.com/docs/hooks/global#transform) hook. See [Providers](https://burger-api.com/docs/core-concepts/providers).

## ctx.ip

The client address from the socket. It never comes from headers like `X-Forwarded-For`. It is set on Bun `serve()` and on [`@burger-api/node-server`](https://burger-api.com/docs/deployment/node). With `toFetchHandler` it is `undefined`.

# Response Mutation

Handlers return a standard `Response`. To change the status, headers or cookies from a hook or a handler, use `ctx.set`. BurgerAPI applies it to the response at the end of the request.

```ts title="src/api/users/route.ts"
import type { BurgerContext } from "burger-api";

export async function POST(ctx: BurgerContext) {
  ctx.set.status = 201;
  ctx.set.headers = {
    "x-total": "42",
    "set-cookie": "session=abc; HttpOnly; Path=/",
  };
  return Response.json({ created: true });
}
```

What you get:

- `ctx.set.status` changes the status of a success response. An error status (400 or higher) stays as it is.
- `ctx.set.headers` adds headers. Your values win over the response's own headers.
- An array value adds every entry. `set-cookie` is always added, so cookies from the handler and from `ctx.set` both reach the client.
- A `ctx.set` from `onRequest` also applies to 404s, errors, pages and `/docs`.

To change the response body or read the response, use an [after hook](https://burger-api.com/docs/hooks/after) instead.

# Deployment

Build your app with `burger-api build`, then run it on your target. Each target has its own guide:

- [Bun](https://burger-api.com/docs/deployment/bun): `burger-api build`, then `burger-api start`.
- [Node.js](https://burger-api.com/docs/deployment/node): `serve(app)` from `@burger-api/node-server`.
- [Cloudflare Workers](https://burger-api.com/docs/deployment/cloudflare)
- [Vercel](https://burger-api.com/docs/deployment/vercel)
- [Deno](https://burger-api.com/docs/deployment/deno)

Edge targets use `toFetchHandler(app)`. See [CLI Build](https://burger-api.com/docs/cli/build) and [Build Exec](https://burger-api.com/docs/cli/build-exec).
